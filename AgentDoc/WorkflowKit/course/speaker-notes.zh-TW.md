# Workflow 90 分鐘講者教案

現行教學依 skills 與共享資源；course/sources/ 是歷史快照。新 GitHub 流程以人工 trace 與實際手動合併為關卡。

## 00–08｜先看整張地圖

目標：區分 OpenSpec、Issue、PR、人工 trace 與知識整理的責任。

- 0–2 分：用「資源不足時不得發送」介紹貫穿案例，這是教學假設而非已完成實驗。
- 2–5 分：四個名詞各給一個檔案或操作例子。
- 5–8 分：沿主線走一遍，讓學員用自己的話重述。

示範：沿流程指出「人工接受」「分支已準備歸檔」「PR 已合併」三個不同狀態。

提問：archive 資料夾已存在，這個 change 就完成了嗎？

參考答案：新 GitHub 流程還須核對手動合併及 Issue 收尾；本地歸檔準備不代表遠端整合。

停止條件：只看進度不開始實作；已提供的工具連結不代表工具目前可用。

## 08–18｜六面向訪談與紀錄

目標：用問題、選項與備註形成有證據的需求，而不是直接指定目錄。

- 前 3 分：一題一個決策，以實例協助理解。
- 中間 4 分：練習選項＋備註與可續談紀錄。
- 最後 3 分：示範題數上限、假設與實作前回問。

示範：以校園失物招領示範：先改善查找還是認領管理？給出選項、例子與備註，再記錄未決條件。

提問：第 10 題仍不知道資料是否可公開，是否可以先當成同意？

參考答案：不可以。記錄未知與影響並討論其他面向；實作前回問。題數用完時先說明，討論縮小範圍或允許追加。

停止條件：不知道資源單位或拒絕副作用時，先補定義；不自行替使用者決定。

## 18–30｜Archify 架構與模組責任

目標：說明 interface 的義務，並判斷新抽象是否必要。

- 前 4 分：以資源單位示範領域詞彙與實作參數的不同。
- 中間 5 分：畫 before／after，讓學員用 deletion test 挑戰新 wrapper。
- 最後 3 分：說明只在真實架構摩擦時使用 improve-codebase-architecture。

示範：畫出照片上傳的輸入欄位、驗證、保存與回應；指出目前已實作與仍屬設計的部分。

提問：把所有函式縮成一行，module 就更 deep 嗎？

參考答案：不是。深度取決於 interface 的能力與認知負擔，而不是程式行數比例。

停止條件：未找到 owner 就不另建平行實作；既有設計足夠就停止架構掃描。

## 30–42｜寫規格時就帶入架構

目標：知道四種 artifact 的責任與依賴順序。

- 前 4 分：四份文件各看一個短段落。
- 中間 5 分：請學員把「回傳拒絕」與「不產生發送副作用」分開列驗收。
- 最後 3 分：講 CLI 動態路徑；下載包不保證各版本都有本專案延伸欄位。

示範：只讀示範：openspec list --json。挑一個既有 change，對照 proposal、design、specs、tasks 各回答哪個問題。

提問：將 send_count = 0 只寫在 tasks，漏在 specs，可以嗎？

參考答案：會失去行為要求的權威來源。先在 specs 定義，再讓 tasks 連到檢查。

停止條件：需求或驗收改變時回到 OpenSpec；不得從勾選完成推論 runtime 成功。

## 42–52｜依問題選擇工具

目標：正確區分 MCP、CLI、文件與實際權限。

- 前 3 分：畫 host → client → server → resource／tool；補一條 shell → CLI。
- 中間 4 分：以 caller／diff／PDF／結果發布四種題目分組選工具。
- 最後 3 分：對照安裝指南，區分工具已安裝、MCP 已註冊、agent 實際呼叫成功；未實測平台不能宣稱通過。

示範：比較「修正記帳功能」與「整理研究文件」：各自需要哪些能力，哪些工具不必啟動？

提問：工具出現在安裝清單中，是否代表本次可以直接使用？

參考答案：不代表。仍須確認實際介面、安裝與存取狀態，以及它是否能提供本任務所需證據。

停止條件：不執行未填妥的範本命令，不複製他人機器的健康狀態與絕對路徑。

## 52–65｜人工 trace、PR 與手動合併

目標：區分程式驗證、人類接受、PR 檢查與實際合併。

- 前 4 分：示範每項行為的局部語意檢查，再對照整體 review 與 tech_improve.md 的延後改善。
- 中間 5 分：展示英文 docs/output.md 與繁體中文前後對照；練習先結論後細節，檢查排版與必要限制，依需要才讀範例。
- 最後 4 分：練習 awaiting_merge、手動合併與 head 變更的複驗。

示範：比較：測試通過但人工未接受；人工接受但 PR 未合併；PR 合併但缺結案整理。指出各自的下一步。

提問：PR 開好而且 CI 綠燈，auto 模式能開始下一個 change 嗎？

參考答案：不能。使用者手動合併且 Agent 核對實際結果後，auto 才能接續；change 模式則回報並停下。

停止條件：PR 尚未合併、CI 證據不適用目前 head 或人工接受缺失時，不標記完成、不開始下一個 change。

## 65–80｜原位整理與訪談學習

目標：說明論文機制與本專案採用範圍，拒絕無證據自動演進。

- 前 4 分：從 README 找到訪談、規格、trace 與封存。
- 中間 6 分：比較明示偏好、推測與反證。
- 最後 5 分：說明事件證據與隔離候選的資格。

示範：兩次獨立訪談都太晚發現回復需求：整理共同根因與反證，而不是直接把偏好寫入全域 skill。

提問：使用者這次要求離線，是否代表所有專案都要離線？

參考答案：不是。這是帶有適用範圍的需求；推測成長期偏好需要確認，跨專案共用尚未定案。

停止條件：Wiki 同意不代表 Skill 啟用；來源不足不宣稱成功。回饋紀錄不再次觸發遞迴評估。

## 80–90｜局部驗證，再決定推廣

目標：完成一次候選拒絕判斷，知道下載包如何使用。

- 前 4 分：區分 Wiki、隔離候選與 active skill；合格候選撰寫才讀 writing-for-agents，精簡不能刪除必要行為。
- 中間 5 分：比較兩個不同任務與一次重跑，討論版本變更後為何重驗。
- 最後 3 分：展示 management/ 範本、$workflow 啟動提示與本機先驗證的回家作業。

示範：練習：候選通過同一任務兩次，另一個新任務卻漏了拒絕情境。判斷能否建議推廣。

提問：候選格式檢查通過，就可以更新共用 Skill 嗎？

參考答案：不行。還需不同任務的實際品質證據、沒有必要驗收退步，以及使用者對指定版本與目標的啟用決定。

停止條件：結構檢查不證明 Agent 品質；兩次同任務不算兩個任務，候選不能自行降低啟用門檻。
