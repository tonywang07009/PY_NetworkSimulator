# 繁體中文寫作前後對照

這些範例用來理解 [共通寫作規範](output.md)，不是交付狀態或驗證證據。


以下全部是寫法示例，沿用本次討論的 trace 情境；它們不代表功能已實作、
測試已新增或流程已通過驗收。實際輸出必須換成當次核對的事實。

### CLI：「這個 change 在做什麼？」

修改前：

> 本次調整 archive gate，補上 trace artifact 與路徑驗證，並更新 workflow
> handoff。人工確認獨立處理，相關證據於收尾彙整。

修改後：

> 審核者需要先取得架構圖與程式導讀，才能確認本次變更是否符合需求。因此，
> 本次將架構圖與 `code-trace.md` 的更新移到人工 trace 之前。
>
> 人工 trace 通過後，workflow 才接續規格同步與歸檔。若帶讀過程發現問題，
> Agent 會先修正程式、更新文件並完成必要複驗，再交由使用者確認。
>
> 歸檔會改變 change 文件的位置，因此收尾時還需要檢查文件連結，確保審核者
> 能從歸檔紀錄找到對應的規格、程式與測試證據。

此例先交代審核者的需要，再介紹修改；後兩段沿用「人工 trace」與「歸檔」
推進流程與收尾理由。讀者不需要先理解 gate、artifact 或 handoff 才能跟上。

### CLI：「目前做到哪裡？」

修改前：

> trace 已更新，sync pending，archive blocked。

修改後：

> 架構圖與程式導讀已更新，目前等待您進行人工 trace。您確認後，Agent 會把
> 本次已核准的需求更新同步到正式規格，再將 change 歸檔。

此例將狀態名詞轉成實際完成項目、等待事項與後續動作；沿用既有授權，
不把每個階段交接改成新的許可問題。

### 驗證說明：測試結果能支持什麼？

修改前：

> 新增路徑測試；CI 待執行。

修改後：

> 歸檔後仍須能開啟文件中的連結，因此本次新增移動後的路徑檢查案例。
> CI 尚未執行，目前只能確認已有測試案例，尚不能宣稱檢查通過。

實際有執行結果時，接上命令、版本與證據位置，並說明檢查涵蓋到哪一種行為。

### Issue／PR：版面保持，改善章節內文

假設現有 PR template 的章節是「做了什麼」，章節名稱保持原樣。

修改前：

> 完成 trace lifecycle 整合與 archive path reconciliation，改善 reviewability。

修改後：

> 審核者需要在歸檔前讀到完整的架構與程式導讀。本次讓 workflow 在人工
> trace 前更新這兩份資料，並於歸檔後核對文件連結，讓審核者能繼續找到
> 當時的規格、程式與驗證證據。

後續沿用該 PR 原有閱讀順序、流程圖、人工檢核、模組關聯與驗證章節。
