# 專案文件管理與訪談學習說明

本文件記錄本次討論確認的文件管理方式，並提出訪談學習的整合設計。
適用對象是使用本套件的目標專案；此教材庫本身不建立活動中的 interview/、
OpenSpec、Wiki 或個人 workflow 狀態。更新日期：2026-10-18。

## 目前狀態與責任

| 項目 | 狀態／負責位置 |
|---|---|
| 每個 change 的 code-trace.md、路徑與證據 | 已有規範，見 [code trace 指引](../skills/openspec-archive-change/references/code-trace.md) |
| 知識整理、品質候選評估與驗證 | 已有 [llm-wiki](../skills/llm-wiki/SKILL.md) 與 [skill-evolution](../skills/skill-evolution/SKILL.md) |
| 訪談資料夾、命名、P.A.R.A 導覽、結案整理 | 已接入 grill-with-docs、workflow 與 Wiki 交接；成效需實際案例驗證 |
| 討論後的架構圖、人工 trace 前完整文件 | 已接入 workflow 的 architecture 指引與 archive／apply 交接 |
| 從訪談辨識關注點並回饋訪談品質 | 已接入 Wiki／skill-evolution 證據流程；實際成效尚待案例驗證 |
| 根目錄 /AGENTS.md 忽略追蹤 | 根目錄限定 /AGENTS.md 已加入 .gitignore；本機檔案保留，未改寫舊位置的搬移紀錄 |
| GitHub 交付與寫作 | 一個 change／Issue／PR，人工 trace 後同 PR 交付，使用者手動合併；共通寫作見 output.md |
| 決策詢問與人讀文件 | 問題、選項、工具問答介面及文件起草／修改均遵循 [output.md](output.md) |
| 局部語意檢查與技術債 | 每個可驗證行為核對規格與測試；change review 執行 code-review、ponytail-debt；合理延後事項留在 OpenSpec 根目錄 tech_improve.md |
| CLM 評測、tag 與跨專案偏好共用 | CLM 列未來待辦，Jev／TypeSafe 不再採用；tag 與跨專案自動傳遞仍待設計 |

OpenSpec 擁有正式需求、設計與驗收；訪談保留需求形成過程；Archify 與 trace
呈現其衍生視圖；Wiki 整理有來源的知識；skill-evolution 管理技能改進候選。
同一規則只由對應位置維護，其餘文件用連結引用。訪談與現行規格衝突時，
記錄差異並釐清，不讓舊紀錄靜默覆蓋目前需求。

## 一、檔案結構與命名

以下為校園失物招領專案的示例，不是本教材或任何現有專案的實際檔案清單。
src/、tests/ 與 OpenSpec 均沿用目標專案真實結構；CLI 管理路徑由 CLI 解析。
有等效文件時更新既有文件，只在有具體內容時建立新的研究、維護或知識文件。

```text
/projects/campus-lost-found/
├── README.md                            # 專案入口、操作方式與文件導覽
├── AGENTS.md                            # 本機 Agent 規則；只忽略根目錄此檔
├── interview/
│   ├── README.md                        # 訪談索引、狀態與相關 change
│   └── 2026-10-15-campus-lost-found.md    # 同一 workflow 的持續訪談紀錄
├── docs/
│   ├── architecture/
│   │   ├── system.archify.json           # 目前整體架構來源
│   │   └── system.html                   # 目前整體架構圖
│   ├── research/
│   │   └── item-search-comparison.md     # 文獻、候選方案與權衡
│   └── maintenance.md                   # 長期維護責任與方式
├── src/                                 # 程式沿用實際 owner
├── tests/                               # 需求對應測試
└── openspec/
    ├── tech_improve.md                   # 實際有延後事項時建立；穩定 TI 編號與重評條件
    ├── specs/                           # 正式現行規格
    └── changes/archive/
        └── 2026-10-22-add-item-search/
            ├── proposal.md
            ├── design.md
            ├── tasks.md
            ├── specs/
            ├── architecture.archify.json
            ├── architecture.html        # 本 change 詳細架構快照
            └── code-trace.md            # 本 change 的實作、測試與人工導讀
```

| 類型 | 命名方式 | 規則 |
|---|---|---|
| 訪談 | YYYY-MM-DD-work-topic.md | 日期是起始日期；跨天續談不改名，同一工作沿用同一紀錄 |
| 同日同主題的獨立工作 | YYYY-MM-DD-work-topic-2.md | 先確認不是續談，再用遞增尾碼避免覆寫 |
| 研究／比較 | topic-purpose.md | 例如 item-search-comparison.md，依主題與用途命名 |
| 整體架構 | system.archify.json、system.html | 固定名稱，表示目前版本；歷史差異交給 Git |
| change 架構 | architecture.archify.json、architecture.html | 由 change 目錄識別範圍與版本 |
| 導讀 | code-trace.md | 沿用現有名稱，避免另建 code_trace.md 造成兩份紀錄 |
| 技術債 | tech_improve.md | 位於實際 OpenSpec 根目錄；以穩定 TI 編號追蹤，不因 change 歸檔而搬移 |
| 索引 | README.md | 根目錄負責專案導覽，interview/ 負責訪談導覽 |

新檔名預設使用小寫英文與連字號，文件標題與說明可用繁體中文。
既有檔案不因命名風格不同而批次改名。狀態寫在文件內，不使用 final、new、
latest 等尾碼表示完成度。範本 management/AGENTS.md 繼續隨套件配送；
根目錄限定的 /AGENTS.md ignore 不擴及巢狀範本。

一般導覽使用相對連結；code-trace.md 同時保留專案相對路徑、擷取時的絕對路徑、
重要符號與 Git revision／未提交範圍。絕對路徑描述當時機器位置，移機後以
相對路徑重新定位。歸檔後驗證實際路徑與連結；刪除檔案標為歷史資料，
不假裝是可開啟的現存檔案。實際 tree 由受影響範圍產生，標明省略的分支。

## 二、P.A.R.A 是導覽分類

| 分類 | 本工作流的用途 | 導覽目標 |
|---|---|---|
| Projects／專案 | 有目標與完成條件的工作 | 進行中訪談、目前 OpenSpec change |
| Areas／領域 | 持續負責與維護的事項 | 操作說明、維護規範、責任與品質要求 |
| Resources／資源 | 可供後續工作重用的資料 | 文獻、方法比較、有來源的知識摘要 |
| Archives／封存 | 已完成工作的歷史證據 | 已結束訪談索引、OpenSpec archive、當時架構與 trace |

檔案保留原位，在專案 README 的導覽表中按上述用途列出連結、摘要與狀態。
同一文件可從多個用途入口找到，但只維護一份正文。專案結束後，訪談仍在
interview/，研究仍在原研究位置；OpenSpec 按既有流程歸檔。

例如查找「為什麼第一版只支援關鍵字搜尋」：

```text
專案 README → 搜尋方案比較 → 訪談決策段落 → 正式 OpenSpec
            → 歸檔 code-trace.md → 實作符號與測試證據
```

文件分類是本次對 P.A.R.A 的應用，不要求把程式與測試移進四個新資料夾。

## 三、訪談紀錄如何建立與續用

在目標專案開始獲授權的訪談時，先檢查 interview/ 與其索引：不存在才建立；
已存在則確認目前工作並更新原紀錄。路徑若被一般檔案占用，或指向不明的外部
symlink，先釐清，避免覆寫。安裝套件本身不建立活動紀錄。

| 區段 | 內容 |
|---|---|
| 基本資訊 | 工作識別、日期、狀態、目標專案、相關 change／正式規格連結 |
| 訪談進度 | 六面向的題數、已回答與待回答項目；續談沿用計數 |
| 已確認決策 | 使用者可見的問題、選項、答案、備註、原因與適用範圍 |
| 證據 | 文獻／原始資料位置與章節，區分已讀、未讀、已驗證與待驗證 |
| 未決事項 | 暫用假設、風險、受影響工作、實作前要再問的問題 |
| 交付連結 | 整體／change 架構、OpenSpec、trace、實際 archive 與驗收結果 |

每面向最多 10 題，包含追問與最後澄清；每次一題、以 2～3 個選項及選填備註
為主，給一個貼近專案的實例。已回答問題沿用，不為了湊題而重問。
訪談時需預留實作前澄清的額度；已達上限仍有未決事項時，記錄後先討論其他
面向。實作前回到未決清單詢問；若額度已用完仍需追加，先明示此衝突，
請使用者選擇縮小本次範圍或允許追加，避免靜默重置計數。
依賴未決事項的實作等待回答；可獨立進行的工作繼續。

紀錄保留結論所需的問答與依據，不收集隱藏推理或無關私密資訊。
已結束紀錄保留原始決策；後續發現錯誤時，附日期註記並連到取代它的新決策，
不把舊答案改寫成彷彿當時就已知道的內容。

## 四、架構、人工 trace 與專案收尾

| 時點 | 文件工作 |
|---|---|
| 討論形成決策後 | 從訪談建立 Archify 整體概覽與相關細節；未確認部分標示假設 |
| 規格形成後 | 架構引用正式 OpenSpec；保留訪談到正式決策的來源連結 |
| 每個可驗證行為完成後 | 核對 OpenSpec、實作、呼叫端／設定與測試；範圍內缺陷直接修正並複驗 |
| 實作與測試完成後 | code-review 對照規範與 OpenSpec，ponytail-debt 盤點標記；具體架構問題交 improve-codebase-architecture 整理 |
| 人工 trace 前 | 更新完整架構圖與 code-trace.md，涵蓋輸入結構、內部流程、輸出結構、軟工技術及理由 |
| 人工 trace | 先整體、再 change、再實際檔案／符號；逐段停下供使用者提問與確認 |
| 修改後 | 更新圖與 trace，執行必要複驗，取得適用於最終內容的人工確認 |
| 人工接受後、PR 前 | 同步規格、準備歸檔並驗證連結，更新 README；與程式同 PR 交付 |
| PR 等待與完成 | Agent 處理回饋，由使用者手動合併；核對結果、版本與 Issue 收尾後完成，才考慮下一個 change |
| 全部 change 已合併與全案驗收後 | 原位整理相關索引、摘要、知識與訪談學習證據，完成必要結案後計一次 workflow |

目前整體架構可隨後續 change 更新；已歸檔的 change 圖與 trace 保留當時快照。
技術債的分類、重評與結案依 [technical-debt.md](../skills/workflow/references/technical-debt.md)；
登記不是免除驗收，沒有標記也不代表沒有技術債。
專案結案整理是事件觸發，不代表已設定定時背景排程。只讀相關索引與本次變動，
不為收尾而掃描無關專案、搬移原始檔或刪除舊資料。沒有新內容時不製造重複更新。

完成整理時，實際從 README 嘗試找到「怎麼用」、「為何這樣做」、「程式在哪裡」
三類資料，記錄可達位置與斷鏈。查找速度若要宣稱改善，需比較相同查找任務；
連結檢查通過本身不代表效率已提升。

## 五、訪談如何持續學習

執行交接沿用既有「來源 → Wiki 知識 → skill-evolution 評估 → 候選驗證」流程，
訪談是新增的證據來源，不另做一套自我修改機制。知識位置由目標專案 context
解析，沿用既有 Wiki 索引、sources、patterns 與 log；需要候選時才建立 evolution。

| 層次 | 例子 | 對後續訪談的影響 |
|---|---|---|
| 使用者明確表達 | 「每題給選項與備註」 | 記錄原話、日期、來源與範圍，在適用範圍直接沿用，無須等待兩次事件 |
| Agent 觀察／假設 | 多次追問失敗回復，可能重視資料可靠性 | 標為 [Needs Verification]；用來提出較相關的問題，不當成已確認偏好或需求 |
| 需求與約束 | 第一版限定離線使用 | 保留在對應專案規格，不能推論所有後續專案都必須離線 |
| 訪談方法問題 | 同一問題重問、例子引導錯誤、重要限制問得太晚 | 記錄根因與實際後果，交既有 skill-evolution 評估是否有改進候選 |

每項關注點至少帶有來源段落、時間、適用範圍、確認狀態、例外／反證及被哪個
新決策取代。後續只讀與當前問題相關的索引與來源；原始問答保留在原訪談。
新指示與舊偏好衝突時，以目前明確指示為準並註記取代關係；無法判斷則詢問。
使用者可更正或撤回偏好，衍生摘要需同步更新。

學習的目的是減少重問、提早發現重要限制，並保持方案比較涵蓋競爭觀點。
使用者重視某個方案，不能成為忽略反對證據的理由。預設先限定本專案，
跨專案共用何種偏好仍待討論；此文件不授權寫入個人全域記憶或共享技能。

### 實例：從關注點到技能改進

| 事件 | 可保留的結論 | 後續處理 |
|---|---|---|
| 訪談甲：使用者明說需要失敗回復說明 | 此工作需要說明失敗與回退；是否為長期偏好尚未確認 | 後續相關問題提供失敗情境與選項 |
| 獨立訪談乙：再次太晚詢問回復需求，導致重設計 | 可能存在「訪談過晚揭露可靠性限制」的共同根因 | 連結兩次事件與成功／失敗證據，提出有範圍的評估 |
| 候選在新案例中更早發現限制 | 僅能說明已測案例的結果 | 比較 baseline／candidate，檢查其他需求沒有漏問 |

以上是示例，不代表已發生兩次事件或已證明技能改善。兩次引用同一份訪談、
同一問題的重述，不能算兩個獨立事件。

### 沿用既有 skill-evolution 門檻

實際門檻由 [資格規則](../skills/skill-evolution/references/eligibility.md)、
[候選比較](../skills/skill-evolution/references/evaluation.md) 與
[啟用規則](../skills/skill-evolution/references/promotion.md) 維護。
目前要求重複根因的獨立事件、適用的成功／失敗證據與可執行比較；
穩定候選須通過不同任務，包含未參與候選撰寫的案例。

每次已完成的 Wiki 更新使用同一 update／assessment ID 交接，續作沿用結果；
缺資料時回報不足與下一個最小證據工作。回饋寫回原紀錄，不遞迴啟動新評估。
只改文件格式或通過檢查器，不能宣稱 Agent 已學會更好的訪談。
候選保持隔離，正式啟用沿用既有指定版本／目標的使用者授權規則。
本次要求訪談學習不等於已核准任何尚未產生的候選。新流程的原位整理與
有界 capture 是既有授權的結案工作；舊流程保留原本選填同意紀錄。

套件測試與 verify.py 可檢查安裝、連結與校驗碼；以下成效仍需目標專案案例：
訪談是否減少重問、是否正確掌握關注點、是否發現反證、認知負荷是否合適、
人工 trace 是否能找到真實程式，以及資料查找是否較容易。尚未執行者標為
[Needs Verification]，不以文件存在或字串檢查宣稱完成。

## GitHub 與狀態的完成界線

正式程序由 [github.md](../skills/workflow/references/github.md) 維護。
新流程預設 GitHub 交付；Issue 在 OpenSpec 確認後追蹤進度，完整文件先交付再
人工 trace。接受後在同一分支準備規格同步、歸檔、README，隨程式同 PR 送審。
由使用者手動合併，Agent 核對實際結果。prepared／awaiting_merge 不算完成；
下一個 change 必須等前一個 merged。舊版 local 紀錄保留，不重寫過去計數。
合併後的觀察紀錄留在本機證據與索引，不回寫成已合併 PR 中原本存在的證據。
